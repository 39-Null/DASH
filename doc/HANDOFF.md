## 4. 上一阶段：模型构建工作（全部实测，已完成 / 部分中断）

### 4.1 V0 快速验证（已完成）

用两个零成本开源项目在单台笔记本上验证了端到端链路与双源架构（详见技术路线报告第 2 节）：

| 组件 | 技术本质 |
|---|---|
| SysMocap v0.8.0（身体） | MediaPipe Holistic 关键点 + Kalidokit **规则式逆运动学**（非端到端网络） |
| miniface 0.1.0（面部） | MediaPipe Tasks FaceLandmarker，**神经网络直接回归** ARKit 52 BlendShape |
| 融合服务器（我方编写） | socket.io + WebSocket 统一数据流 |

**实测**（i7-10750H，无 GPU）：身体约 13 FPS（单跑）/ 6–8 FPS（双源同跑）；面部 2.5–3 FPS；融合约 22 FPS；同步误差 3–334 ms。文档声称 30–60 FPS，实测只有 13，**后续规划一律用实测值**。

### 4.2 量化探针（阶段 0）：三问与证据

| 问 | 结论 | 证据 |
|---|---|---|
| Q1 能拆出 `.tflite`？ | 是 | `.task` 是无压缩 ZIP，3 个 `.tflite` + 1 份几何元数据，尺寸自校验吻合（合计 3,758,024 + 572 = 3,758,596 B） |
| Q2-A 能转 ONNX？ | 1/3 | 只有 `face_detector` 转成功（30 个固定种子输入，误差中位数 8.678e-05，保真达标）；另两个崩在 `tflite2onnx` **内部**（是转换器 bug，不是算子不支持） |
| Q2-B 自产数据集 | 完成 | 1500 样本，`X(1500,1434)` / `Y(1500,52)` float32，无 NaN，坐标 `[-0.085, 1.046]`，标签 `[0, 0.991]` |
| Q3 能测三数？ | 是 | 度量工具校准到 11.916 ms（与独立方法 11.7–13.2 ms 互证，两把尺子一致才可信） |

**关键结论**：真正产生微表情的 `face_blendshapes.tflite`（955 KB）**转不了 ONNX**，所以必须自训一个小网络（知识蒸馏）替代它——这也正好补面试「知识蒸馏」考点。

### 4.3 实测数据汇总（硬件 Intel Core Ultra 5 255H / i7-10750H，CPU only）

| 量 | 值 |
|---|---|
| 摄像头采集率 | 30.0 FPS（硬件上限） |
| 面部管线推理 | 11.7–13.2 ms（占 33 ms 帧预算 36%） |
| 冷启动 | 约 2.4 s |
| 基准延迟 mean / p50 / p95 / min | 11.916 / 11.737 / 13.981 / 10.303 ms |
| 测量噪声 | 约 5%（mean）/ 11.6%（p95） |
| `.task` 容器 | 3,758,596 B（3 模型 + 1 元数据） |
| 可转 ONNX | 1/3（`face_detector.onnx` = 425,659 B） |
| 数据集样本 | 1500 |
| 死通道 | 52 个 BlendShape 里 **14 个从未激活**（标签 std < 0.01） |

**帧预算算术**：推理 11.9 ms 占 33.3 ms 的 36%，**当前瓶颈已在摄像头一侧**，量化不会提升现有管线帧率；其价值在更高分辨率、多模型并发、或迁移到更弱设备时。

### 4.4 方法论发现（推翻了早期结论，面试高分素材）

1. **欠定线性系统静默过拟合**：1434 未知数 > 1200 方程 → 训练集 R²=1.0 是死记硬背。**不做容量控制，架构比较无意义**（比的是谁过拟合少）。加 L2 后 val R² 从 0.74 升到 0.95。
2. **随机划分跨时间泄露**：相邻帧相似度是远距离帧的 21 倍 → 随机划分 val R²=0.95 vs 时间划分 0.63。**时序数据不能随机划分。**
3. **INT8 量化的弱点**：拟合权重重尾（max/std=14.2，高斯应 ~4）+ 1434 项累加（√n≈38）+ 大量抵消 → per-tensor 量化误差**超过**模型自身误差。per-channel 权重量化改善 3.9 倍。累加在 INT32 里精确，误差不随层内加法累积。
4. **单次测量判定不可复现**：阈值判定翻转率 33%，必须固定种子 + N 次输入 + 中位数。

### 5.2 任务解读（我的判断，用户未反驳）

- **皮套人** = 一个 3D 角色（VRM 格式），像皮套一样罩在真人脸上——你做什么表情，它跟着做什么表情。

### 5.5 三条技术路线与我的推荐

| 方案 | 架构 | 优势 | 劣势 |
|---|---|---|---|
| **A 全浏览器单页（推荐）** | MediaPipe Tasks JS + three.js/VRM 都在浏览器 | 与 pollo.ai 同构、单页零依赖、部署简单、补前端缺口 | 要写 JS |
| B Python 后端 + 浏览器渲染 | FastAPI 跑 MediaPipe，WS 推到浏览器 | 全 Python 栈 | 两进程、有延迟、不像 pollo.ai 一键 |
| C 改造 miniface | 清理第三方 UI | 最快 | 别人的代码，不是「我们的项目」；依赖重 |

**我推荐 A**。理由：① 与参考同构（全客户端）；② 演示稳健（单页少一个进程就少一个故障点）；③ 部署简单（静态文件随便放）；④ 正好补用户的前端 JS/TS 面试缺口（P2）；⑤ 皮套人渲染**无论哪条路线都得在浏览器用 JS**，Python 只省感知层一小段，却多付两个进程的复杂度，不划算。

**已坦白的风险**：浏览器里 MediaPipe Tasks JS 的帧率可能不如 Python（miniface 假摄像头下 2.5–3 FPS，但那是假摄像头瓶颈不是模型）。做的时候实测，若不够 15 FPS，再讨论降级方案（降分辨率 / 隔帧处理）。
